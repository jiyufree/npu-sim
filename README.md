# Mini NPU Simulator

입력 패턴과 필터를 위치별로 곱하고 더하는 **MAC(Multiply-Accumulate) 연산**으로
십자가(Cross)와 X 패턴을 판별하는 Python 콘솔 시뮬레이터입니다.
3×3부터 25×25까지 크기별 연산 시간을 측정해 **O(N²)** 시간 복잡도를 확인합니다.

---

## 1. 실행 방법

- **환경**: Python 3.8 이상, 표준 라이브러리(`json`, `time`, `re`, `os`, `sys`)만 사용 (NumPy 등 외부 라이브러리 없음)
- **실행**: `npu-sim` 폴더에서

```bash
python main.py                       # 모드 선택 메뉴
python main.py data_error_test.json  # 모드 2에서 다른 JSON 파일을 분석할 때
```

- **data.json 위치**: `main.py`와 같은 폴더. 경로를 `main.py` 기준으로 찾기 때문에 다른 폴더에서 실행해도 됩니다.

| 선택 | 모드 | 흐름 |
|---|---|---|
| `1` | 사용자 입력 (3×3) | 필터 A, B 입력 → 저장 확인 → 패턴 입력 → MAC 연산 → 판정(A/B/판정 불가) → 성능 분석(3×3) |
| `2` | data.json 분석 | 필터 로드 → 패턴 로드·검증 → MAC/판정/PASS·FAIL → 성능 분석(3×3, 5×5, 13×13, 25×25) → 결과 요약 |
| `3` | 패턴 생성기 (보너스) | N 입력 → N×N Cross/X 자동 생성 → 판정 → 성능 분석 |

잘못된 메뉴 번호나 형식 오류 입력은 안내 문구를 출력하고 다시 입력받습니다.


## 3. 구현 요약

### 데이터 구조
- 패턴과 필터는 `list[list[number]]` 형태의 n×n 2차원 리스트로 저장합니다.
- `get_value(m, r, c)` / `set_value(m, r, c, v)`로 특정 위치 값을 읽고 씁니다.
- `validate_square()`가 "정사각형인지, 모든 값이 숫자인지"를 검사해 크기 n을 반환합니다.

### MAC 연산
- `mac(pattern, filt)`: 이중 `for` 문으로 같은 위치끼리 곱한 값을 `total`에 누적하고 float로 반환합니다.
- 외부 라이브러리나 `sum()`/`zip()` 같은 내장 함수에 기대지 않고, 반복문으로 직접 구현했습니다.

### 라벨 정규화
프로그램 내부에서는 표준 라벨 **`Cross`, `X`** 두 가지만 사용합니다.

| 원래 값 | 위치 | 표준 라벨 |
|---|---|---|
| `+`, `cross`, `plus` | expected / 필터 키 | `Cross` |
| `x`, `ex`, `×` | expected / 필터 키 | `X` |

앞뒤 공백을 지우고 소문자로 바꾼 뒤 매핑합니다(`Cross`, ` X ` 등도 처리). 매핑에 없는 값은 `None`이 되고, 해당 케이스는 `[라벨]` 사유로 FAIL 처리합니다.
콘솔 출력과 PASS/FAIL 비교는 모두 표준 라벨로 합니다.

### 점수 비교 정책 (epsilon)
- `abs(score_a - score_b) < 1e-9`이면 **동점 → UNDECIDED** (모드 1에서는 "판정 불가")
- 그 외에는 점수가 큰 쪽의 라벨로 판정합니다.
- UNDECIDED는 Cross도 X도 아니므로 expected와 절대 같을 수 없어 **FAIL(동점 규칙)** 으로 기록됩니다.

### 모드 2 스키마 검증 (케이스 단위 FAIL)
케이스마다 아래 순서로 검사하고, 문제가 생기면 프로그램을 멈추지 않고 **그 케이스만 FAIL + 사유**로 처리합니다.

1. 키가 `size_{N}_{idx}` 형식인가 → 정규식으로 N 추출
2. `input`, `expected` 키가 있는가
3. `expected`를 표준 라벨로 정규화할 수 있는가
4. `input`이 정사각 숫자 배열이고 크기가 N인가
5. `size_N` 필터에 Cross와 X가 모두 있고, 각 필터 크기가 N인가 (필터는 로드 단계에서 미리 검증)

파일 없음이나 JSON 문법 오류는 안내 메시지를 출력한 뒤 정상 종료합니다.
그 밖에 예상하지 못한 예외도 케이스 단위로 잡아 `[예외]` 사유로 기록합니다.

### 성능 측정 방식
- `time.perf_counter()`로 **연산 함수 호출 구간만** 측정합니다 (입력·출력·파일 읽기, 1차원 변환 시간 제외).
- 크기별로 워밍업 1회를 실행한 뒤 **10회 반복 측정한 평균**을 ms 단위로 출력합니다.
- 표에는 크기 / 평균 시간(ms) / 연산 횟수(N²)와 함께, O(N²) 확인용으로 **N²당 시간(ns)** 도 출력합니다.

## 4. 결과 리포트

### 4-1. data.json 실행 결과

```
총 테스트: 6개   (size_5_1, size_5_2, size_13_1, size_13_2, size_25_1, size_25_2)
통과: 6개
실패: 0개
```

| 케이스 | Cross 점수 | X 점수 | 판정 | expected(원본 → 정규화) | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 1.0 | 9.0 | X | `x` → X | PASS |
| size_5_2 | 9.0 | 1.0 | Cross | `+` → Cross | PASS |
| size_13_1 | 1.0 | 25.0 | X | `x` → X | PASS |
| size_13_2 | 25.0 | 1.0 | Cross | `+` → Cross | PASS |
| size_25_1 | 1.0 | 49.0 | X | `x` → X | PASS |
| size_25_2 | 49.0 | 1.0 | Cross | `+` → Cross | PASS |

### 4-2. 왜 FAIL이 0개가 되었는가

1. **라벨 정규화**: data.json의 expected는 `+`, `x`이고 필터 키는 `cross`, `x`입니다. 판정 결과(`Cross`/`X`)와 문자열을 그대로 비교했다면 `"Cross" != "+"`가 되어 **6개 모두 FAIL**이 났을 것입니다. 이런 실패는 로직 오류가 아니라 **데이터 표기(라벨/스키마) 문제**입니다. 비교 전에 양쪽을 표준 라벨로 정규화해서 이 문제를 없앴습니다.
2. **필터 선택 규칙**: 키 `size_13_2`에서 정규식으로 N=13을 뽑아 `size_13` 필터를 고릅니다. `key.split('_')[1]`처럼 위치에 의존하지 않고 형식 전체를 검사하므로, 형식이 다른 키는 엉뚱한 필터와 계산되지 않고 FAIL 사유로 걸러집니다.
3. **epsilon 비교**: 이번 데이터는 0/1 정수라 점수 차가 최소 8 이상이어서 동점이 없었습니다. 하지만 실수 데이터에서는 `0.1 + 0.2 = 0.30000000000000004`처럼 수학적으로 같은 값이 다르게 계산됩니다. 이때 `>`로만 비교하면 무작위에 가까운 판정이 나오므로, 1e-9 미만 차이는 동점으로 처리하는 정책을 적용했습니다.

### 4-3. 의도적 오류 데이터 검증 (`data_error_test.json`)

예외 처리가 제대로 동작하는지 확인하려고 오류 케이스를 모은 파일을 따로 만들었습니다 (`python main.py data_error_test.json`).
결과는 **총 9개, 통과 1개, 실패 8개**이고, 프로그램은 중단되지 않았습니다. 실패 원인은 과제의 세 가지 분류로 나뉩니다.

| 케이스 | 넣은 오류 | 출력된 사유 | 분류 |
|---|---|---|---|
| size_5_2 | 4×4 패턴 | `[크기] 패턴 4×4 ≠ 키의 5×5` | 데이터/스키마 |
| size_5_3 | 행 길이가 들쭉날쭉 | `[스키마] input 정사각형이 아닙니다` | 데이터/스키마 |
| size_5_4 | expected `circle` | `[라벨] 알 수 없는 expected 값` | 데이터/스키마 |
| size_5_6 | expected 누락 | `[스키마] 'expected' 항목 없음` | 데이터/스키마 |
| size_7_1 | 없는 크기의 필터 | `size_7의 Cross, X 필터를 사용할 수 없음` | 데이터/스키마 |
| size_13_1 | X 필터가 11×11 | `size_13의 X 필터를 사용할 수 없음` | 데이터/스키마 |
| pattern_a | 키 형식 위반 | `[스키마] 키 형식 오류` | 데이터/스키마 |
| size_5_5 | Cross=0.1+0.2, X=0.3 | `[동점] UNDECIDED 처리 규칙에 따라 FAIL` | 수치 비교 |

- **로직 문제**를 진단할 때는 판정 사유가 `[판정] 판정 X ≠ expected Cross`처럼 나옵니다. 스키마와 라벨이 정상인데도 판정이 틀렸다는 뜻이므로, MAC이나 비교 코드를 의심하면 됩니다.
- size_5_5는 `0.30000000000000004`와 `0.3`의 차이(약 5.5e-17)가 epsilon보다 작아 UNDECIDED가 되었습니다. epsilon 없이 비교했다면 "Cross 승"으로 PASS가 나왔겠지만, 그것은 부동소수점 오차가 우연히 만든 결과입니다. 동점을 명시적으로 FAIL로 드러내는 쪽이 더 정직한 정책이라고 판단했습니다.

### 4-4. 성능 분석과 시간 복잡도 O(N²)

모드 2 실행 결과 (10회 평균, 실행 환경에 따라 값은 달라질 수 있음):

| 크기(N×N) | 평균 시간(ms) | 연산 횟수(N²) | N²당 시간(ns) |
|---|---|---|---|
| 3×3 | 0.0006 | 9 | 약 70 |
| 5×5 | 0.0011 | 25 | 약 46 |
| 13×13 | 0.0055 | 169 | 약 32 |
| 25×25 | 0.0184 | 625 | 약 30 |

**해석**
- `mac()`은 `for i in range(n): for j in range(n):` 이중 반복문으로 n×n 칸을 정확히 한 번씩 방문하며 곱셈 1번, 덧셈 1번을 합니다. 따라서 연산 횟수는 정확히 **N²** 이고, 시간 복잡도는 **O(N²)** 입니다.
- N이 5에서 25로 5배 커지면 연산 횟수는 25배(25 → 625)가 됩니다. 측정 시간도 0.0011ms에서 0.0184ms로 약 17배 늘어 **N²에 비례해 증가**합니다. N에 비례(5배)하는 것보다 훨씬 가파릅니다.
- 마지막 열(N²당 시간)이 13×13 이후 약 30ns로 **거의 일정**해집니다. 시간 = (상수) × N² 이라는 뜻이므로 O(N²)의 직접적인 근거가 됩니다.
- 작은 크기(3×3, 5×5)에서 N²당 시간이 더 큰 이유는 함수 호출, 반복문 준비, 타이머 호출 같은 **고정 비용**이 연산 수가 적을 때 상대적으로 크게 보이기 때문입니다.
- 1회 연산이 마이크로초 단위라 OS 스케줄링 등의 영향으로 측정값이 흔들릴 수 있습니다. 실제로 반복 실행 중 5×5가 0.0038ms로 튀는 경우도 있었습니다. 그래서 워밍업 1회를 제외하고 10회 평균을 사용했습니다.
- 25×25 필터 하나도 625번의 MAC이 필요합니다. 실제 AI 모델은 이런 연산을 수억 번 수행하므로, CPU처럼 하나씩 순서대로 처리하는 대신 수천 개의 MAC을 병렬로 처리하는 NPU가 필요합니다.

## 5. 보너스 과제

### 5-1. 1차원 배열 최적화 (`mac_flat`)
2차원 리스트를 길이 N²인 1차원 리스트로 펼쳐(`flatten`) 인덱스 하나(`k`)로만 접근합니다. 동일 입력, 동일 반복 횟수(10회)로 비교한 결과는 다음과 같습니다.

| 크기 | 2D(ms) | 1D(ms) | 1D/2D |
|---|---|---|---|
| 3×3 | 0.0006 | 0.0005 | 0.78 |
| 5×5 | 0.0011 | 0.0008 | 0.73 |
| 13×13 | 0.0056 | 0.0047 | 0.84 |
| 25×25 | 0.0184 | 0.0192 | 1.04 |

작은 크기에서는 바깥 반복문과 행 꺼내기(`pattern[i]`)가 사라져 15~25% 빨라졌습니다. 25×25에서는 차이가 측정 오차 범위 안이었습니다.
2D 버전도 이미 행을 변수(`p_row`)에 담아 한 번만 꺼내도록 작성했기 때문에 차이가 크지 않습니다. 두 방식 모두 연산 횟수는 N²으로 같으므로 **복잡도는 O(N²) 그대로이고 상수만 줄어든다**는 것을 확인할 수 있습니다.

### 5-2. 패턴 생성기 (`generator.py`, 모드 3)
- `make_cross(n)`: 가운데 행과 열을 1로 채운 십자가 패턴
- `make_x(n)`: 두 대각선을 1로 채운 X 패턴
- 모드 3에서 N을 입력하면 생성된 패턴으로 판정과 성능 분석을 수행합니다. 성능 분석(`perf.py`)과 `data.json` 생성에도 같은 생성기를 재사용했습니다.

## 6. 학습 목표 정리

1. **MAC 연산과 AI에서의 중요성**: 입력과 필터의 같은 위치 값을 곱하고 누적하는 연산입니다. 이미지 한 장에도 수억 번 필요하기 때문에, 이를 병렬로 처리하는 NPU가 등장했습니다.
2. **유사도(점수) 원리**: 필터의 1이 있는 자리에 입력의 1이 많이 겹칠수록 점수가 높아집니다. 5×5 X 입력은 X 필터와 9칸이 겹쳐 9점이고, Cross 필터와는 중앙 1칸만 겹쳐 1점입니다.
3. **라벨 정규화 이유**: 데이터 작성자마다 `+`, `cross`, `x`처럼 표기가 다릅니다. 내부 표준(Cross/X)으로 통일해야 비교 로직이 한 가지 규칙으로 동작합니다.
4. **부동소수점과 epsilon**: 2진수로 표현할 수 없는 실수는 오차가 생기고, 누적 연산에서는 오차도 커집니다. 그래서 `==`/`>` 대신 허용오차 기반으로 비교합니다.
5. **O(N²)**: 연산 횟수가 N²이고, 측정한 N²당 시간이 거의 일정하다는 점으로 확인했습니다.
6. **실패 진단**: 사유 태그(`[스키마]`/`[크기]`/`[라벨]` → 데이터, `[판정]` → 로직, `[동점]` → 수치 비교)로 원인을 바로 분류할 수 있게 했습니다.
